Qual das duas? Para o banco funcionar, precisamos de colunas cujo valor nunca se repete. Essas colunas formam uma chave.

Tabela baseada no exemplo do livro, p. 37.

Chave primária (PK)

Na tabela Clientes, ClienteID e CNPJ nunca se repetem. Entre as colunas assim, escolhemos uma para ser a chave primária (primary key, PK).

Regras da PK:

  • Uma só por tabela (pode ter mais de uma coluna).
  • Nunca se repete.
  • Nunca fica vazia (não aceita NULL).
  • Não deveria mudar com o tempo.
Chave substituta (surrogate)

Em vez de usar um dado do negócio (CNPJ), criamos uma coluna só para identificar: ClienteID, um número sem significado.

O SGBD preenche sozinho com AUTO_INCREMENT: 1, 2, 3…

E o CNPJ? Continua sem poder repetir. Na aula 4 marcamos como UNIQUE.

Livro, 10.3 e 10.3.1, p. 36–37.

Chave estrangeira (foreign key, FK): coluna de uma tabela que guarda o valor da chave primária de outra.

É assim que tabelas se relacionam: Vendas não repete o nome do cliente, só guarda o seu número.

Integridade referencial O SGBD só aceita na FK um valor que exista na PK referenciada. Venda para o cliente 99? Recusada: não existe cliente 99.

Livro, 10.3.2, p. 38–39 · MariaDB: Foreign Keys

Do DER às tabelas

Três regras transformam o desenho da aula 2 em esquema lógico.

Regra 1 — entidade vira tabela

  • Cada entidade vira uma tabela.
  • Cada atributo vira uma coluna.
  • O identificador vira a chave primária.

Um atributo com vários valores (um cliente com 3 telefones) não cabe numa coluna. Vira outra tabela.

PRODUTOS ➜

Produtos

  • ProdutoID
  • Nome
  • Descricao
  • Preco
  • Estoque

Regra 2 — no 1:N, a FK vai para o lado N

CLIENTES1 compraN VENDAS

Clientes

  • ClienteID
  • Nome
  • CNPJ
  • …

Vendas

  • VendaID
  • DataVenda
  • TotalVenda
  • ClienteID

A tabela do lado muitos (Vendas) ganha uma coluna com a PK do lado um (Clientes).

Por que não o contrário? Se a FK ficasse em Clientes, cada cliente só poderia apontar para uma venda. Já cada venda aponta para um cliente, e vários podem apontar para o mesmo.

A FK pode ficar vazia? Pergunte ao negócio: "toda venda tem cliente?" Sim → NOT NULL.

Regra 3 — N:N vira tabela com duas FKs

Vendas

  • VendaID
  • DataVenda
  • TotalVenda
  • ClienteID
  • FuncionarioID

ItensVenda

  • ItemVendaID
  • VendaID
  • ProdutoID
  • Quantidade
  • PrecoUnitario

Produtos

  • ProdutoID
  • Nome
  • Descricao
  • Preco
  • Estoque

A tabela associativa recebe uma FK para cada lado, mais os atributos do relacionamento.

PK da associativa: opção AChave substituta ItemVendaID. É o que o livro usa e o que faremos.
Opção BChave composta (VendaID, ProdutoID): o par não se repete. Vai aparecer na lista, na BiblioTech.

E o 1:1? A FK vai para qualquer um dos lados, ou as duas entidades viram uma tabela só.

CNPJ, CEP e telefone são texto, não número. Ninguém soma CEPs, e um INT apagaria o zero da frente de 01000000.
Dinheiro é DECIMAL, nunca FLOAT. Tipos de ponto flutuante arredondam, e centavos somem.

NULL: a ausência de valor

Clientes
NomeTelefoneEmail
Oficina Fernanda & Filhos43992224455NULL
Retífica CarmenNULLcarmen@retifica.com.br

NULL significa "não sei" ou "não se aplica".

  • NULL não é zero.
  • NULL não é texto vazio ''.
Lógica de três valores Qualquer comparação com NULL não dá verdadeiro nem falso: dá desconhecido (o próprio NULL). 
SELECT 1 = NULL;     -- NULL
SELECT NULL = NULL;  -- NULL

Consequência prática (aula 5): para achar quem não tem e-mail, escrevemos Email IS NULL, nunca Email = NULL.

Ao modelar, decida coluna por coluna: pode ficar sem valor? Se não pode: NOT NULL.

Revisão relâmpago

1. Qual destas colunas de Clientes é a melhor chave primária?

  1. Nome
  2. CEP
  3. ClienteID
Nunca se repete, nunca fica vazia e não muda. Nome e CEP se repetem (as duas Carmens).

2. No relacionamento 1:N entre Clientes e Vendas, a FK fica em…

  1. Clientes
  2. Vendas
  3. uma terceira tabela
Sempre do lado N. Terceira tabela é só para N:N.

3. Uma venda feita pelo site não tem funcionário. A coluna FuncionarioID de Vendas deve…

  1. ser NOT NULL
  2. aceitar NULL
  3. virar chave primária
Se o negócio permite venda sem funcionário, a FK pode ficar vazia.
