Qual das duas? Para o banco funcionar, precisamos de colunas cujo valor nunca se repete. Essas colunas formam uma chave.

Tabela baseada no exemplo do livro, p. 37.

Superchave e chave candidata

Superchave: qualquer conjunto de colunas que identifica cada linha de forma única. Pode ter colunas sobrando.

  • {ClienteID} ✔
  • {CNPJ} ✔
  • {CNPJ, Nome} ✔ Nome está sobrando
  • {ClienteID, CNPJ, Nome, CEP} ✔ quase tudo sobrando
  • {Nome} ✘ duas Carmens
  • {Nome, CEP} ✘ mesma Carmen, mesmo CEP

Chave candidata: superchave mínima. Se tirar qualquer coluna, deixa de identificar.

  • {ClienteID} ✔
  • {CNPJ} ✔
  • {CNPJ, Nome} ✘ não é mínima
Toda chave candidata é superchave. Nem toda superchave é chave candidata.

Livro, 10.1 a 10.3, p. 34–36 (Elmasri & Navathe, 2011).

Chave primária (PK)

Das chaves candidatas, escolhemos uma para ser a chave primária (primary key, PK). As outras ficam como chaves alternativas.

Regras da PK:

  • Uma só por tabela (pode ter mais de uma coluna).
  • Nunca se repete.
  • Nunca fica vazia (não aceita NULL).
  • Não deveria mudar com o tempo.
Chave substituta (surrogate)

Em vez de usar um dado do negócio (CNPJ), criamos uma coluna só para identificar: ClienteID, um número sem significado.

O SGBD preenche sozinho com AUTO_INCREMENT: 1, 2, 3…

E o CNPJ? Continua sem poder repetir. Na aula 4 marcamos como UNIQUE.

Livro, 10.3 e 10.3.1, p. 36–37.

Chave estrangeira (foreign key, FK): coluna de uma tabela que guarda o valor da chave primária de outra.

É assim que tabelas se relacionam: Vendas não repete o nome do cliente, só guarda o seu número.

Integridade referencial O SGBD só aceita na FK um valor que exista na PK referenciada. Venda para o cliente 99? Recusada: não existe cliente 99.

Livro, 10.3.2, p. 38–39 · MariaDB: Foreign Keys

Bloco 2 · 35 min

Do DER às tabelas

Três regras transformam o desenho da aula 2 em esquema lógico.

Regra 1 — entidade vira tabela

  • Cada entidade vira uma tabela.
  • Cada atributo vira uma coluna.
  • O identificador vira a chave primária.

Um atributo com vários valores (um cliente com 3 telefones) não cabe numa coluna. Vira outra tabela. Voltamos a isso na 1ª forma normal.

PRODUTOS ➜

Produtos

  • ProdutoID
  • Nome
  • Descricao
  • Preco
  • Estoque

Regra 2 — no 1:N, a FK vai para o lado N

CLIENTES(1,1) faz(0,N) VENDAS

Clientes

  • ClienteID
  • Nome
  • CNPJ
  • …

Vendas

  • VendaID
  • DataVenda
  • TotalVenda
  • ClienteID

A tabela do lado muitos (Vendas) ganha uma coluna com a PK do lado um (Clientes).

Por que não o contrário? Se a FK ficasse em Clientes, cada cliente só poderia apontar para uma venda. Já cada venda aponta para um cliente, e vários podem apontar para o mesmo.

Mínimo 1 → a FK é obrigatória (NOT NULL). Mínimo 0 → a FK pode ficar vazia.

Regra 3 — N:N vira tabela com duas FKs

Vendas

  • VendaID
  • DataVenda
  • TotalVenda
  • ClienteID
  • FuncionarioID

ItensVenda

  • ItemVendaID
  • VendaID
  • ProdutoID
  • Quantidade
  • PrecoUnitario

Produtos

  • ProdutoID
  • Nome
  • Descricao
  • Preco
  • Estoque

A tabela associativa recebe uma FK para cada lado, mais os atributos do relacionamento.

PK da associativa: opção AChave substituta ItemVendaID. É o que o livro usa e o que faremos.
Opção BChave composta (VendaID, ProdutoID): o par não se repete. Vai aparecer na lista, na BiblioTech.

E o 1:1? A FK vai para qualquer um dos lados (de preferência o opcional), ou as duas entidades viram uma tabela só.

NULL: a ausência de valor

Clientes
NomeTelefoneEmail
Oficina Fernanda & Filhos43992224455NULL
Retífica CarmenNULLcarmen@retifica.com.br

NULL significa "não sei" ou "não se aplica".

  • NULL não é zero.
  • NULL não é texto vazio ''.
Lógica de três valores Qualquer comparação com NULL não dá verdadeiro nem falso: dá desconhecido (o próprio NULL). 
SELECT 1 = NULL;     -- NULL
SELECT NULL = NULL;  -- NULL

Consequência prática (aula 5): para achar quem não tem e-mail, escrevemos Email IS NULL, nunca Email = NULL.

Ao modelar, decida coluna por coluna: pode ficar sem valor? Se não pode: NOT NULL.

Livro, cap. 10, p. 33–34 · MariaDB: NULL Values

Normalização

Um teste em três etapas para achar redundância escondida nas tabelas.

Por que normalizar: as anomalias

Anomalia de atualizaçãoO cliente mudou de nome: preciso alterar 3 linhas. Se esquecer uma, o banco fica inconsistente.
Anomalia de inserçãoNão consigo cadastrar um produto novo antes de ele ser vendido: não há VendaID para a linha.

Normalizar é aplicar regras (as formas normais) que eliminam essas anomalias dividindo a tabela.

Livro, 10.3.3, p. 39–40.

2ª forma normal: depender da chave inteira

2FN: está na 1FN e nenhuma coluna depende só de uma parte da chave primária. Só existe risco quando a PK é composta.

3ª forma normal: depender só da chave

3FN: está na 2FN e nenhuma coluna comum depende de outra coluna comum.

✘ Vendas

VendaID → ClienteID → ClienteNome. O nome do cliente depende da venda só indiretamente, passando pelo ClienteID. É uma dependência transitiva.

Correção: o que depende de ClienteID vai para a tabela Clientes. Em Vendas fica só a FK.

Para lembrar Toda coluna depende da chave (1FN), da chave inteira (2FN) e de nada além da chave (3FN).

Livro, p. 42–45. Existem formas normais acima da 3FN; no dia a dia, chegar à 3FN é o alvo.

Em que forma normal está?

 Em dupla. Diga qual forma normal cada tabela viola e como corrigir.

A. Funcionarios(FuncionarioID, Nome, Cargo, SalarioBaseDoCargo) — o salário base é definido pelo cargo.

B. Produtos(ProdutoID, Nome, Fornecedores) — a coluna Fornecedores guarda 'Bosch, NGK, Cofap'.

C. Matriculas(AlunoID, ModalidadeID, DataMatricula, NomeModalidade)

A viola a 3FN: FuncionarioID → Cargo → SalarioBaseDoCargo. Criar Cargos(CargoID, Nome, SalarioBase) e deixar em Funcionarios a FK CargoID.

B viola a 1FN: lista dentro da célula. Como um produto tem vários fornecedores e um fornecedor vende vários produtos (N:N), criar Fornecedores e a associativa ProdutosFornecedores(ProdutoID, FornecedorID).

C viola a 2FN: NomeModalidade depende só de ModalidadeID, parte da chave. Mover para Modalidades(ModalidadeID, Nome).

Revisão relâmpago

1. Uma chave candidata é uma superchave…

  1. com mais de uma coluna
  2. sem nenhuma coluna sobrando
  3. que aponta para outra tabela
É a superchave mínima.

2. No relacionamento 1:N entre Clientes e Vendas, a FK fica em…

  1. Clientes
  2. Vendas
  3. uma terceira tabela
Sempre do lado N. Terceira tabela é só para N:N.

3. Uma coluna comum que depende de outra coluna comum viola a…

  1. 1FN
  2. 2FN
  3. 3FN
Dependência transitiva. "Nada além da chave."
